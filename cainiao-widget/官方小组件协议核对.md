# 菜鸟官方小组件取数协议核对

日期：2026-11-09。目标：参考菜鸟自带小组件，定位首次 App 接入后可独立运行的取数方式。

**本轮取得了官方 Android 8.11.1105 的具体实现证据，并据此实现 1.3.0 的有条件接入。研究开始时生产为 1.2.4；本版当前发布状态见验证记录。没有取得菜鸟 iOS 扩展样本，不能将以下 Android 行为称为 iOS 实测，也没有完成本人手机的独立查询验收。**

下载实际返回 HTTP 200，97,262,943 字节。资源清单中的包名为 `com.cainiao.wireless`，版本为 8.11.1105，版本码为 478。原始 APK 的 SHA-256：

只用已有工具静态解析资源与反汇编字节码，没有安装或执行样本。APK、拆解目录和证据记录只保存在仓库外研究目录，不随组件发布。没有读取私人 HAR、手机凭据或 App 私有存储，没有从电脑发送登录或个人包裹请求。

## 实际流程

```text
本人 App 的原生登录会话
  → 原生 MTOP 签发小组件专用 token
  → 保存 WIDGET_TOKEN
  → 桌面组件用该 token 和新毫秒时间戳发独立 HTTPS JSON 请求
  → 成功后保存本地快照并重绘
```

这与当前产品的 `cookie2/sgcookie → H5 token/sign → 身份/COUNT/PDS` 是两条不同的协议路径。发现官方组件的路径，不等于已经证明旧 H5 请求被拒绝的唯一原因；但后续不能再默认 App Cookie 足够驱动官方组件的独立查询。

### 专用 token 签发

官方 `GuoguoUserWidgetTokenRequest` 声明：

- API：`mtop.cainiao.guoguo.widget.token.get.cn`。
- 版本：`1.0`。
- `NEED_SESSION=true`、`NEED_ECODE=true`。
- 参数：`issuingSystem=guoguo`、`issuingBusiness=widget`。

`WidgetRequestUtil` 使用 `CNMtopBusinessUtils.obtainCNMtopBusiness(...)`，随后调用 `useWua()` 和 `startRequest(TokenResponse.class)`。成功监听器从 `data.result` 读取非空字符串，保存为 `WIDGET_TOKEN`，再调用包裹查询。

因此它是服务端签发的**小组件专用凭据**，不是 `_m_h5_tk`、`x-sid` 或由 Cookie 改名得到的值。字节码只将它当作不透明字符串；本轮没有验明其内部账号字段、有效期或独立续期协议。签发依赖 App 原生登录及其 MTOP 能力，不能照搬成 Egern 的匿名 HTTP 请求或重放一次性原生签名。

### 独立包裹查询

官方生产地址：

```text
https://guoguouser.cainiao.com/com.cainiao.guoguo.guoguouser.widget.WidgetLogisticsService/1.0.0/queryWidgetDetailsV2
```

`WidgetRequestUtil` 新建默认 OkHttp 客户端，通过 **POST** JSON 请求体直接发请求。POST 方法由原 APK `classes3.dex` 的 OkHttp 请求构造实现另行确认。该方法没有调用 H5 签名构造器，也没有在这里附加原生 `x-sign`。实际声明的请求头为：

```text
Http-Rpc-Type: JsonContent
Content-Type: application/json
```

请求体采用 `WidgetPkgRequest`：

- `argsTypes`：只有 `com.cainiao.guoguo.guoguouser.widget.domain.WidgetRequest` 一项。
- `argsObjs`：只有一个请求对象。
- 对象中的 `token`：本机保存的 `WIDGET_TOKEN`。
- `timestamp`：每次请求重新取当前毫秒时间戳。
- Android 样本的固定值：`appName=GUOGUO_APP`、`source=Android`。
- `version`：按 App 的包裹授权模式取 1 或 2，不能认定两者无条件等价。
- `ext`：JSON 字符串 `{"apiVersion":"V3"}`，不是直接嵌套对象。
- `channel`、`brand`、`installStatus` 来自 App 实际环境；`lbs` 只在有定位权限及有效坐标时提供。不能将 Android 的设备值或来源标识当作 iOS 的实际值。

具体代码证据：`widgetprovider/request/b$a.smali` 第 298–380 行读取并放入 token，第 385–525 行构造业务参数，第 527–648 行构造生产地址、JSON 请求及请求头，第 652–661 行直接 `enqueue`。这些行号对应本轮保存的反汇编结果，不是官方源码行号。

### 刷新与失败

真实 Android manifest 注册五个桌面 provider，绑定的资源 XML 声明 `updatePeriodMillis=1800000`。系统 `onUpdate` 在原生已登录时调用包裹请求方法。30 分钟只是 Android 的声明，不是当前 iOS 的刷新保证。

成功响应模型为 `NewWidgetData`，含 `success`、`code`、`data`。代码要求 `success=true`：

- `data.status=INVALID_TOKEN`：清除包裹缓存，再通过 App 原生 MTOP 重新签发专用 token。
- `data.status=QUERY_ERROR`、`success=false` 或网络失败：读取旧缓存；旧缓存展示不能计为一次新查询成功。
- 其余成功结果：保存 `PKG_LOCAL_CACHE_V3`，发包内更新事件后重绘。
- JSON 解析异常：只记录日志后返回，未见显式缓存回退调用，不能概括为所有失败都会回退缓存。

本地更新事件只重绘，不等于发新请求。主页的打开时间记录和红点更新也不发包裹查询。没有证据可声称 Egern 能在专用 token 失效后自行调用原生续期。

## 返回的包裹与取件信息

真正显示的主要字段是 `data.packageInfo`：

- `agentSignPackNum`：官方待取件界面直接显示的数量，不用数组长度或多个状态计数之和替代。
- `packageItemInfoList`：官方组件的包裹摘要。
- 摘要 `logisticsStatus=900`：官方待取件分类；`10101` 为派送分类。未命中待取分类时，不能复制官方退回任意第一条包裹的显示行为。
- 待取件主行原样显示 `logisticsStatusSimpleDesc`，副行显示 `stationName`。

这个模型没有独立的 `authCode` 字段。`hasAuthCode` 只用于选择“查看取件码”的 App 内入口，不能当作码值，也不能据此从任意描述中的数字猜一个取件码。后续可如实显示官方摘要，但不能宣称已经得到结构化取件码。

请求和返回模型没有页码、游标或 `hasNext` 合同。`packageInfoV2.agentSignNum` 在另一计数映射中使用，语义未验明，不能与 `packageInfo.agentSignPackNum` 互换。返回摘要、数量和完整 PDS 列表是不同层次的结果：

- 待取数量大于零而没有对应摘要，应明确显示“有待取包裹，摘要未提供”。
- 数量为零或摘要为空，不作为完整个人列表已经查全的证明。
- 不把本轮摘要接口接入的可能性写成完整列表和取件码目标已经完成。

## 对当前产品的决定

1.3.0 已围绕**真实服务端签发的 widget token 与上述独立查询合同**实现专用响应、实际模板和新的独立 POST，而不是继续给拒绝的 H5 Cookie 改名、换网关或补提示。凭据仍只留在本人手机；接入保留账号归属、账号切换隔离、失败停止和并发写回保护。只有实际手机出现同一合同才启用。

手机验收仍需确认：

1. 当前菜鸟 iOS 自带组件实际调用哪条 token 签发与查询协议。没有 iOS `.appex` 或手机的同次请求证据，不能把 Android API 视为当前 iOS 已确认入口。
2. 当前 iOS 首次打开 App 是否会生成可捕获的专用 token，以及它的账号归属和参数来源。不要求用户再提供原始 HAR 或发凭据。
3. 本人手机用捕获的真实凭据执行新独立查询；关闭 App 后再执行一次新的查询。按这个接口验收的是新请求时间戳，不凭空要求不存在的 H5 `sign`。
4. 单独确认返回信息是否满足完整待取列表和取件码需求。不能因为专用查询成功而跳过原有全量 PDS 的完成门槛。

同模块的专用 token 捕获、实际参数绑定和独立 POST 已实现，具体约束见方案的 1.3.0 章节；回归与发布证据见[验证记录](验证记录-1.3.0.md)。没有发送电脑个人查询。实质取数代码验证后沿用用户持续发布授权直接发布；Android 静态证据、离线测试和发布均不代表本人 iOS 接通。
