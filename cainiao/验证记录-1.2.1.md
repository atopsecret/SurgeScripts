# 菜鸟去广告 1.2.1：UDP/QUIC 条件修正与缓存复核

日期：2026-11-08，Asia/Shanghai。基线为双端 `1.2.0`，提交 `824e84575096be3538862d8b3c17b3e2ee0c1f29`。本次版本：Surge `1.2.1`，Egern `eg-native-20261108-1.2.1`。

## 这次抓包证明了什么

第四份 HAR 共 135 条请求，来自 Surge iOS `5.23.0`。实际日志中有 65 条拒绝、13 条 Map Local、2 条 URL Rewrite、52 条 HTTP `200` 和 3 条其它 HTTP 状态；菜鸟模块明确处理了 50 条广告 SDK 请求。HAR 没有目标 Mtop 广告 API、版本响应头或脚本下载记录，所以只能确认某个菜鸟规则模块在工作，不能从 HAR 判断手机加载的是 `1.2.0` 还是更早版本。

本地解析 251 条应用日志，其中 60 条 `CN_Mtop` 记录有 55 条 `http3`、5 条 `http2_0rtt_acs`。`Page_Screen_Cpm` 的两组开屏事件均指向同一条自营视频，并标记 `source=100`、`hasAds=1`、`isCache=true`。因此这次看到的画面是之前已经下载到 App 本地的素材；代理规则不能删除 App 私有缓存。

PCAP 共 11,260 个包，存在 draft-29（`ff00001d`）QUIC。按公开的 Initial 密钥派生方法本地解出 23 个 Initial，并从握手得到目标主机名。`netflow-mtop.cainiao.com`、`cn-acs.m.cainiao.com`、`e2e-mtop.cainiao.com`、`nbcps-mtop.cainiao.com` 和 `longquan-mtop.cainiao.com` 都有双向 UDP/443 数据。上一版按离线解析出的 SNI 和 `quic` 标签判断条件，把手机客户端识别协议和域名作为了前提；这不能证明手机已阻止对应的 draft-29 连接。

## 修改内容

协议条件仍只覆盖原来九个精确 MITM 主机，改动如下：

1. 协议从单独的 `QUIC` 改为 `QUIC 或 UDP`，因为 Surge 官方写明 `PROTOCOL,UDP` 会覆盖被识别为 UDP 的 QUIC/STUN。
2. 增加 `DEST-PORT,443`，不影响这些主机的普通 TCP/HTTPS 或其它端口。
3. Surge 目标域名子条件使用 `extended-matching`，让已识别的 TLS SNI、HTTP `Host` 或 `:authority` 参与域名判断。Egern 没有同名字段，因此 Egern 只保留文档化的精确域名条件。

这不是全局 `block-quic=all`。没有封锁全局 UDP/443，没有硬编码本次抓到的 IP，也没有修改 HTTPDNS/AMDC 返回。48 条可还原的 AMDC `mobileDispatch` 响应里没有五个 Mtop 主机，缺少证据去改写协议调度字段；硬改会影响登录、设备安全和普通业务。

## 客户端限制

Surge 官方手册明确写着，不同 QUIC draft 并存时“not all QUIC traffic can be recognized by Surge”。`extended-matching` 也只能使用客户端已经看到的 SNI/Host，不能从加密 UDP 或裸 IP 凭空恢复域名。Egern 规则没有 Surge 的该字段；Egern 的 `block_quic` 是全局或代理策略级配置，不放进菜鸟模块，避免影响其它 App。

因此本次发布可以确认：规则已经覆盖“连接被识别为 UDP、目标域名也被识别、端口为 443”的漏判分支；不能确认这份手机 PCAP 的 draft-29 现在一定被客户端拒绝。如果确认新模块已加载、请求也进入规则系统后，五个目标主机仍有双向 UDP/443，就需要检查域名是否参与匹配以及规则优先级，不能继续把离线 SNI 判断当作成功。全局 QUIC 回退会影响其它 App，本模块没有启用它。已有素材需使用菜鸟自身的清理缓存功能处理；应用内清理是否覆盖全部广告 SDK 缓存，也未真机验证。
